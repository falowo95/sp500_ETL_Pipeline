Architecture

GitHub (main) --push--> GitHub Actions (WIF, no key files)
   --> build+push image, terraform apply, deploy Cloud Run Job + Service, firebase deploy

Cloud Scheduler (1 daily job, OAuth) --Run Admin API--> Cloud Run JOB "sp500-pipeline"
   container runs: airflow db migrate && airflow dags test SP_500_DATA_PIPELINE_v1 <date>
   (ephemeral SQLite metadata inside the container only — nothing persists between runs)

   DAG tasks:
   1. extract   (Tiingo, incremental since watermark; new tickers get full backfill)
   2. upload    raw CSV -> GCS
   3. load      GCS CSV -> BigQuery staging -> MERGE into partitioned/clustered table
   4. dbt build (staging -> intermediate indicators -> marts)
   5. record    pipeline_runs audit row

GCS (raw landing, versioned, 30d lifecycle)
  -> BigQuery raw.sp500_data (partitioned by trade_date, clustered by symbol)
     -> dbt: stg_stocks -> int_stock_daily_metrics -> dim_stock_summary / fct_stock_analysis

Cloud Run SERVICE "sp500-dashboard" (FastAPI, scale-to-zero, public)   Firebase Hosting
  reads the marts + pipeline_runs                                      (this page)

Cloud Monitoring: alert on job failure -> email

Every box above is scale-to-zero. Nothing runs, and nothing is billed, between invocations.

Engineering decisions

  • Why not Cloud Composer? Composer's cheapest environment has a non-trivial always-on minimum cost — for one daily DAG, that dwarfs every other line item in the cost table above. Cloud Run Jobs running airflow dags test once per invocation keeps the DAG-authoring model while eliminating idle cost entirely.
  • Why not Dataproc/Spark? The original pipeline ran a PySpark step on ~500 tickers/day of OHLCV data — a dataset small enough that BigQuery SQL (via dbt) does the same work for free, with less infrastructure. Removing Spark cut the container image by several hundred MB and two of its slowest build layers.
  • The credential leak, and the fix. A `gitleaks` scan of this repo's history turned up a real, previously-leaked Tiingo API key on a public GitHub repo. The key was rotated immediately. The structural fix: every GCP auth path — the Terraform provider, the Python clients, and CI — now goes through Application Default Credentials or Workload Identity Federation. No service-account key file exists anywhere in this project anymore.
  • Incremental loads. The original pipeline re-pulled full history for all tickers, every day, then overwrote the whole target table. That's the dominant cost and runtime driver, not just a BigQuery write-pattern detail. Each ticker now resumes from its own watermark, with new tickers (e.g. newly added to the index) still getting a full backfill — a single global watermark would have silently under-backfilled them.
  • Dbt materializations: table, not incremental. int_stock_daily_metrics stays a full-rebuild table, not incremental, because its trailing-window functions (200-day moving average, etc.) would need a nontrivial lookback-merge to stay correct incrementally — and at this data scale, a full rebuild costs cents. Right-sizing the solution to the actual data volume, deliberately, in both directions.
